# Data model

Source of truth: `packages/db/prisma/schema.prisma`. This document describes every table
in the Phase 1, Phase 2 and Phase 3 schema and the conventions later phases must follow.

## Conventions

- **Primary keys**: UUID (`@db.Uuid`, generated by the application/Prisma)
- **Timestamps**: `timestamptz` in UTC; every mutable table has `created_at` and
  `updated_at`
- **Soft delete**: **not used in Phase 1.** Sessions, invitations and reset tokens expire;
  audit logs are append-only. Soft delete will only be introduced in later phases where
  recovery or audit value justifies it (e.g. invoices) — never as a blanket default.
- **Money (future invoicing/bookkeeping)**: stored as **integer minor units** (öre/cents)
  with an explicit currency code per document. Locked in now so Phases 4–5 don't drift.
- **Locale/currency**: default locale and currency live on `organizations`
  (`locale`, `currency`, default `SEK`); users carry their own `locale` for UI language.
- Table names are snake_case via `@@map`; enum `OrganizationRole` =
  OWNER, ADMIN, ACCOUNTANT, MANAGER, EMPLOYEE, READONLY.

## Tables

### users

Global identity, shared across organizations.

- `email` (unique), `password_hash` (Argon2id), `name`, `locale`
- `is_platform_admin` — instance-level operator flag (failed-jobs admin API); unrelated to
  any organization role

### organizations

Tenant root.

- `name`, `slug` (unique, auto-generated from name with collision suffix), `locale`,
  `currency`, `created_by_id`

### organization_members

User ↔ organization with a role.

- `organization_id`, `user_id`, `role` (enum)
- Unique `(organization_id, user_id)`; index on `user_id`
- Cascade-deletes with either parent

### sessions

Opaque server-side sessions (ADR-0002).

- `token_hash` (unique; SHA-256 of the raw cookie token — the raw token is never stored)
- `user_id`, `active_organization_id` (nullable — the session's current tenant context),
  `expires_at`, `last_used_at`, `ip`, `user_agent`
- Indexes on `user_id` and `expires_at` (cleanup)

### invitations

Invite lifecycle for memberships.

- `organization_id`, `email`, `role`, `token_hash` (unique), `expires_at` (7 days),
  `accepted_at`, `revoked_at`, `invited_by_id` (SetNull on user deletion)
- Pending = not accepted, not revoked, not expired
- Indexes on `organization_id` and `email`

### password_reset_tokens

- `user_id`, `token_hash` (unique), `expires_at`, `used_at` (single-use)

### audit_logs

Append-only audit trail.

- `organization_id` **nullable** — null for events before any org exists (registration,
  login, password reset)
- `actor_user_id` (SetNull so audit survives user deletion), `action` (stable string
  identifier), `entity_type`/`entity_id`, `metadata` JSONB, `ip`, `user_agent`
- Index `(organization_id, created_at DESC)` for the org-scoped audit page; index on
  `actor_user_id`

### outbox_messages

Transactional outbox (ADR-0005) — written in the same transaction as the domain change.

- `type` (doubles as AMQP routing key), `payload` JSONB, `occurred_at`,
  `published_at` (null = pending), `attempts`, `last_error`
- Index `(published_at, occurred_at)` for the relay poll

### processed_messages

Consumer idempotency ledger — at-least-once delivery made effectively once.

- Composite PK `(message_id, consumer)`, `processed_at`

### failed_jobs

Jobs that exhausted retries (dead-lettered), surfaced in the platform-admin API.

- `queue`, `message_type`, `payload` JSONB, `error`, `attempts`, `failed_at`,
  `retried_at` (set when re-enqueued through the outbox)
- Index `failed_at DESC`

## Phase 2 — customers, projects, tasks, comments, attachments, activity

Added by migration `20260713103911_phase2_customers_projects_tasks`. Every table below
carries `organization_id` for tenant isolation and cascade-deletes with its organization.

Enums:

- `CustomerStatus` — `LEAD`, `ACTIVE` (default), `ARCHIVED`
- `ProjectStatus` — `ACTIVE` (default), `ON_HOLD`, `COMPLETED`, `ARCHIVED`
- `TaskStatus` — `TODO` (default), `IN_PROGRESS`, `BLOCKED`, `DONE`, `CANCELLED`
- `TaskPriority` — `LOW`, `MEDIUM` (default), `HIGH`, `URGENT`

### customers

Customer/company registry — the top of the Phase 2 ownership chain.

- `name`, `org_number`, `email`, `phone`, address (`address_line1`, `address_line2`,
  `postal_code`, `city`, `country`), `notes`, `status` (`CustomerStatus`)
- `created_by_id` (SetNull on user deletion)
- Indexes `(organization_id, status)` and `(organization_id, name)` for the filtered/sorted
  list

### customer_contacts

People at a customer. Cascade-deletes with the customer.

- `customer_id`, `name`, `email`, `phone`, `title`, `is_primary`
- FK `customer_id` **Cascade**; indexes on `organization_id` and `customer_id`

### projects

Work engagement, optionally linked to a customer.

- `customer_id` (nullable), `name`, `description`, `status` (`ProjectStatus`),
  `created_by_id` (SetNull)
- FK `customer_id` **SetNull** — deleting a customer detaches its projects rather than
  deleting them
- Indexes `(organization_id, status)` and `(customer_id)`

### tasks

Unit of work, optionally linked to a customer and/or project and assigned to a user.

- `title`, `description`, `status` (`TaskStatus`), `priority` (`TaskPriority`), `due_date`
- `customer_id`, `project_id`, `assignee_id`, `created_by_id` — all **SetNull**, so
  deleting a customer/project/user detaches the task instead of destroying it
- `completed_at` — set when the task first transitions to `DONE`, cleared if it leaves
  `DONE` (see [architecture.md](architecture.md#activity-timeline)); the same transition
  records a `task.completed` activity, audit action and outbox event
- Indexes `(organization_id, status)`, `(organization_id, assignee_id)`, `(project_id)`,
  `(customer_id)`

### comments

Polymorphic note attached to **exactly one** of a customer, project or task.

- `author_id` (SetNull), `body`, plus three nullable parent FKs `customer_id`,
  `project_id`, `task_id`
- The "exactly one parent" rule is **enforced in the service layer** (there is no DB check
  constraint): each polymorphic route sets exactly one FK from its URL, and `resolveEntityRef`
  validates the parent belongs to the organization before the write
- All three parent FKs are **Cascade** — a comment disappears with its parent
- Indexes `(organization_id, customer_id)`, `(organization_id, project_id)`,
  `(organization_id, task_id)`

### file_attachments

Metadata for a file stored in object storage (MinIO/S3). The bytes live under
`storage_key`; clients only ever receive signed, short-lived download URLs.

- `uploaded_by_id` (SetNull), `file_name`, `content_type`, `size` (bytes, server-measured),
  `storage_key` (unique)
- Polymorphic parent: exactly one of `customer_id`, `project_id`, `task_id`, all
  **Cascade** — deleting the parent removes the attachment row (the object is best-effort
  deleted by the service)
- Indexes `(organization_id, customer_id)`, `(organization_id, project_id)`,
  `(organization_id, task_id)`

### activities

Append-only **user-facing** timeline, distinct from the security `audit_logs` table
(see [architecture.md](architecture.md#activity-timeline)).

- `actor_user_id` (SetNull), `type` (stable string, e.g. `customer.created`,
  `task.completed`, `task.status_changed`, `task.assigned`, `comment.added`,
  `attachment.added`), `metadata` JSONB
- `customer_id`, `project_id`, `task_id` — the **denormalized ownership chain**. When an
  activity is recorded for a project or task, the resolved `customer_id` (and `project_id`
  for a task) is copied onto the row so a customer timeline is a single indexed query
  rather than a join across projects and tasks. `resolveEntityRef` computes this chain.
- All three parent FKs are **Cascade**
- Indexes `(organization_id, customer_id, created_at DESC)`,
  `(organization_id, project_id, created_at DESC)`,
  `(organization_id, task_id, created_at DESC)` — one per timeline scope

## Phase 3 — personnel

Added by migration `20260713114021_phase3_personnel`. Seven new tables (plus `employee_id`
columns on `tasks` and `activities`); every table carries `organization_id` and
cascade-deletes with its organization.

The defining concept is **two tiers of employee data**, separated by permission, not by
table: **directory** fields (`personnel.read`) and **sensitive** personal fields
(`personnel.read_sensitive`). The tiers live in the same `employees` row — the split is
enforced in the API's serialization layer (`apps/api/src/lib/mappers-personnel.ts`), which
attaches the sensitive block only for callers who hold `personnel.read_sensitive`. The
columns are never hidden at the database level.

Enums:

- `EmploymentStatus` — `ONBOARDING` (default), `ACTIVE`, `ON_LEAVE`, `OFFBOARDING`,
  `TERMINATED`
- `EmploymentType` — `FULL_TIME` (default), `PART_TIME`, `CONTRACT`, `INTERN`, `TEMPORARY`
- `AbsenceType` — `VACATION`, `SICK`, `PARENTAL`, `UNPAID`, `OTHER`
- `AbsenceStatus` — `PENDING` (default), `APPROVED`, `REJECTED`, `CANCELLED`
- `EmployeeDocumentCategory` — `CONTRACT`, `IDENTIFICATION`, `CERTIFICATE`, `POLICY`,
  `OTHER` (default)
- `ChecklistType` — `ONBOARDING` (default), `OFFBOARDING`

### employees

An employed person. Carries both data tiers.

- **Directory tier** (`personnel.read`): `first_name`, `last_name`, `work_email`,
  `work_phone`, `job_title`, `department`, `employment_status` (`EmploymentStatus`),
  `employment_type` (`EmploymentType`), `start_date`, `end_date` (both `@db.Date`)
- **Sensitive tier** (`personnel.read_sensitive`): `personal_id_number` (personnummer),
  `date_of_birth` (`@db.Date`), home address (`home_address`, `home_postal_code`,
  `home_city`), `personal_email`, `personal_phone`, and emergency contact
  (`emergency_contact_name`, `emergency_contact_phone`, `emergency_contact_relation`)
- `created_by_id` (SetNull on user deletion)
- **Self-referential manager relation** — `manager_id` (nullable) FK to `employees`
  (`EmployeeManager` relation) with **SetNull**: deleting a manager detaches their reports
  rather than deleting them. A cannot-be-your-own-manager check lives in the service layer.
- **Optional Employee ↔ User link** — `user_id` is nullable and **`@unique`** (at most one
  employee per platform user); FK **SetNull**. An employee need not have a login, so this is
  optional, not a foreign-keyed identity.
- Indexes `(organization_id, employment_status)`, `(organization_id, last_name)` for the
  filtered/sorted directory, and `(manager_id)` for the org chart

### employee_notes

Restricted internal notes about an employee — the most sensitive personnel data. Both read
and write require `personnel.read_sensitive` (enforced in the route layer), stricter than
directory access.

- `employee_id` (**Cascade**), `author_id` (SetNull), `body`
- Index `(organization_id, employee_id, created_at DESC)`

### certifications

Employee qualifications and their expiry, for compliance tracking.

- `employee_id` (**Cascade**), `name`, `issuer`, `issued_date`, `expires_at` (both
  `@db.Date`), `notes`
- Indexes `(organization_id, expires_at)` — powers the "expiring soon" dashboard query —
  and `(employee_id)`

### absence_requests

Vacation/sick/parental/other leave with a review workflow.

- `employee_id` (**Cascade**), `type` (`AbsenceType`), `status` (`AbsenceStatus`, default
  `PENDING`), `start_date`, `end_date` (both `@db.Date`), `reason`
- Review fields: `reviewed_by_id` (SetNull), `reviewed_at`, `review_note`; `created_by_id`
  (raw column, no FK relation in the model)
- Indexes `(organization_id, status)` and `(employee_id)`

### employee_documents

Files for an employee, stored in object storage like Phase 2 attachments but with a
category and a sensitivity flag.

- `employee_id` (**Cascade**), `uploaded_by_id` (SetNull), `file_name`, `content_type`,
  `size` (bytes, server-measured), `storage_key` (unique), `category`
  (`EmployeeDocumentCategory`), `is_sensitive` (default `false`)
- `is_sensitive = true` documents require `personnel.read_sensitive` to list or download;
  directory-only viewers are given 404 (existence is not revealed) — see
  [security.md](security.md#personnel-sensitive-data-handling-phase-3)
- Index `(organization_id, employee_id)`

### onboarding_templates

Reusable onboarding/offboarding checklist templates. Applying one to an employee generates
real `tasks` (see [architecture.md](architecture.md#onboarding-automation)).

- `name`, `description`, `type` (`ChecklistType`), `created_by_id` (raw column)
- Index `(organization_id, type)`

### onboarding_template_items

Ordered checklist items belonging to a template. Cascade-delete with the template.

- `template_id` (**Cascade**), `title`, `description`, `due_offset_days` (task due date =
  employee start date, or now, plus this many days), `sort_order`
- Carries `organization_id` for consistency; index `(template_id, sort_order)`

### tasks and activities — Phase 3 additions

Both tables gained a nullable `employee_id` in this migration:

- **`tasks.employee_id`** — links a task to an employee (used by generated onboarding
  tasks). FK **SetNull**, so deleting an employee detaches their tasks rather than
  destroying them. Index `(employee_id)`.
- **`activities.employee_id`** — the denormalized employee scope for the activity timeline,
  matching the existing customer/project/task chain. FK **Cascade** (an employee's timeline
  disappears with the employee). Index `(organization_id, employee_id, created_at DESC)`.

## Phase 4 — quotes & invoicing

Added by migration `20260713153048_phase4_quotes_invoicing`. Nine new tables; every one
carries `organization_id` for tenant isolation and cascade-deletes with its organization.

### Money representation (read this first)

Phase 4 is the first module that stores money, and it does so with a strict, uniform model:

- **All monetary amounts are integer minor units** (öre for SEK; 1 SEK = 100 minor),
  stored as **`BigInt`** columns whose names end in `_minor` (`unit_price_minor`,
  `subtotal_minor`, `tax_minor`, `total_minor`, `amount_paid_minor`, `credited_minor`,
  `line_net_minor`, `line_tax_minor`, `line_total_minor`, `amount_minor`). **Never floating
  point.**
- **Quantities and percentages are `Decimal`**, not money: `quantity` is `Decimal(14,3)`,
  and `discount_percent` / `tax_rate_percent` are `Decimal(5,2)`.
- **Per-line computed amounts are stored** (`line_net_minor`, `line_tax_minor`,
  `line_total_minor`) rather than recomputed on read. Document headers also store their
  rolled-up `subtotal_minor` / `discount_minor` / `tax_minor` / `total_minor` plus a
  `tax_lines` JSONB VAT-per-rate breakdown. This makes a finalized document **immutable**:
  the stored figures are a snapshot, independent of later product-price edits. The server
  computes these deterministically (decimal.js, HALF_UP rounding at the line level — see
  [architecture.md](architecture.md#deterministic-money-phase-4)); the UI never does money
  math.
- Each document carries its own `currency` (default `SEK`), copied from the organization.

Enums:

- `QuoteStatus` — `DRAFT` (default), `SENT`, `ACCEPTED`, `DECLINED`, `EXPIRED`
- `InvoiceStatus` — `DRAFT` (default), `OPEN`, `SENT`, `PARTIALLY_PAID`, `PAID`, `OVERDUE`,
  `CANCELLED`, `CREDITED`
- `PaymentMethod` — `CASH`, `BANK_TRANSFER` (default), `CARD`, `SWISH`, `OTHER`
- `CreditNoteStatus` — `DRAFT` (default), `ISSUED`
- `NumberSequenceKind` — `QUOTE`, `INVOICE`, `CREDIT_NOTE`

### number_sequences

Per-organization, per-document-type monotonic counter — the source of concurrency-safe
document numbers.

- `kind` (`NumberSequenceKind`), `prefix` (e.g. `INV-`), `padding` (default 4), `next`
  (default 1)
- **Unique `(organization_id, kind)`** — exactly one sequence per org per document type
- **Atomic-increment concurrency pattern**: the row is upserted, then updated with an atomic
  `{ next: { increment: 1 } }`, which takes a row-level write lock. Two concurrent
  finalizations for the same org+kind serialize on that lock and receive distinct, gap-free
  numbers — no duplicates, no gaps. The allocation runs **inside the finalize transaction**
  (see [architecture.md](architecture.md#concurrency-safe-document-numbering)).

### products

Reusable catalogue item used to prefill quote/invoice lines. Not a document itself.

- `name`, `description`, `sku`, `unit` (default `piece`), `unit_price_minor` (`BigInt`),
  `currency` (default `SEK`), `tax_rate_percent` (`Decimal(5,2)`, default 25),
  `is_active` (default true), `created_by_id` (raw column, no relation)
- Indexes `(organization_id, is_active)` and `(organization_id, name)`

### quotes

Customer quote/estimate. Editable only while `DRAFT`.

- `customer_id`, `number` (nullable — assigned on send/convert), `status` (`QuoteStatus`),
  `currency`, `issue_date`, `valid_until` (both `@db.Date`), `customer_notes`,
  `internal_notes`
- Money snapshot: `subtotal_minor`, `discount_minor`, `tax_minor`, `total_minor`,
  `tax_lines` (JSONB)
- Lifecycle timestamps: `accepted_at`, `declined_at`; `converted_invoice_id` (nullable,
  **`@unique`**) links an accepted quote to the draft invoice it produced
- `created_by_id` (SetNull)
- **FK `customer_id` is `onDelete: Restrict`** — a customer with quotes cannot be deleted
- `convertedInvoice` FK is **SetNull**
- Unique `(organization_id, number)`; indexes `(organization_id, status)` and `(customer_id)`

### quote_line_items

Ordered lines belonging to a quote. Cascade-delete with the quote.

- `quote_id` (**Cascade**), `product_id` (nullable, raw column — a snapshot, not a live link),
  `description`, `quantity` (`Decimal(14,3)`), `unit_price_minor` (`BigInt`),
  `discount_percent` / `tax_rate_percent` (`Decimal(5,2)`), computed
  `line_net_minor` / `line_tax_minor` / `line_total_minor` (`BigInt`), `sort_order`
- Index `(quote_id, sort_order)`

### invoices

The billing document. Editable only while `DRAFT`; **immutable once finalized** (number
assigned, `finalized_at` set) — corrections are made via credit notes, not edits.

- `customer_id`, `number` (nullable until finalize), `status` (`InvoiceStatus`), `currency`,
  `issue_date`, `due_date` (both `@db.Date`), `customer_notes`, `internal_notes`
- Money snapshot: `subtotal_minor`, `discount_minor`, `tax_minor`, `total_minor`, plus the
  live position `amount_paid_minor` and `credited_minor` (used to derive `amountDueMinor` =
  total − paid − credited and the status). `tax_lines` (JSONB)
- `pdf_storage_key` — object-storage key of the generated PDF (set at finalize)
- Lifecycle timestamps: `finalized_at`, `sent_at`, `paid_at`, `cancelled_at`,
  `last_reminder_at`
- `created_by_id` (SetNull)
- **FK `customer_id` is `onDelete: Restrict`** — a customer with invoices cannot be deleted
- `fromQuote` back-relation exposes the originating quote (if converted)
- Unique `(organization_id, number)`; indexes `(organization_id, status)`,
  `(organization_id, due_date)` (overdue sweep) and `(customer_id)`

### invoice_line_items

Same shape as `quote_line_items` but parented to an invoice (`invoice_id`, **Cascade**).
Once the invoice is finalized these rows are frozen. Index `(invoice_id, sort_order)`.

### payments

A payment recorded against an invoice.

- `invoice_id` (**Cascade**), `amount_minor` (`BigInt`), `method` (`PaymentMethod`),
  `reference`, `paid_on` (`@db.Date`), `note`, `created_by_id` (SetNull)
- Registering/removing a payment recomputes the invoice's `amount_paid_minor` and status;
  **overpayment is rejected server-side** (a payment cannot exceed the amount due)
- Index `(organization_id, invoice_id)`

### credit_notes

A full or partial credit against a finalized invoice. Fully crediting an invoice moves it to
`CREDITED`.

- `invoice_id` (**Cascade**), `number` (nullable until issued, `CN-` prefix), `status`
  (`CreditNoteStatus`), `currency`, `issue_date` (`@db.Date`), `reason`
- Money snapshot: `subtotal_minor`, `tax_minor`, `total_minor`, `tax_lines` (JSONB),
  `issued_at`; `created_by_id` (SetNull)
- Issuing a credit note recomputes the invoice's `credited_minor` and status;
  **over-crediting is rejected server-side** (total credited cannot exceed the invoice total)
- Unique `(organization_id, number)`; index `(organization_id, invoice_id)`

### credit_note_line_items

Lines belonging to a credit note (`credit_note_id`, **Cascade**). Same computed-amount
columns as the other line-item tables (no `discount_percent`). Index
`(credit_note_id, sort_order)`.

## Phase 5 — bookkeeping (double-entry ledger)

Added by migration `20260713171720_phase5_bookkeeping`. Seven new tables; every one carries
`organization_id` for tenant isolation and cascade-deletes with its organization. This is the
second money module, so it follows the Phase 4 convention: **all amounts are integer minor
units** (öre; 1 SEK = 100 minor) stored as **`BigInt`** columns whose names end in `_minor`
(`debit_minor`, `credit_minor`, `total_debit_minor`, `total_credit_minor`). **Never floating
point.**

The core concept is a **voucher** (verifikation) — a numbered, dated journal entry whose
lines must **balance** (Σ debit = Σ credit) before it can be posted. Posted vouchers are
**immutable** and corrected only by reversing vouchers (see
[architecture.md](architecture.md#voucher-posting--immutability-phase-5) and
[ADR-0006](decisions/adr-0006-double-entry-voucher-model.md)).

Enums:

- `AccountType` — `ASSET`, `LIABILITY`, `EQUITY`, `REVENUE`, `EXPENSE` (an account's normal
  balance side is derived from the type; `ASSET`/`EXPENSE` are debit-normal)
- `FiscalPeriodStatus` — `OPEN` (default), `LOCKED`, `CLOSED` (shared by fiscal years and
  periods; only an `OPEN` period accepts postings)
- `VoucherStatus` — `DRAFT` (default), `POSTED`, `REVERSED`
- `VoucherSource` — `MANUAL` (default), `INVOICE`, `PAYMENT`, `OPENING_BALANCE`

The `NumberSequenceKind` enum (Phase 4) gained a **`VOUCHER`** value (prefix `V-`, padding 5),
so posted vouchers draw a concurrency-safe per-org number from the same `number_sequences`
mechanism as invoices (see [architecture.md](architecture.md#concurrency-safe-document-numbering)).

### accounts

Chart-of-accounts entry — a typed, per-organization account addressed by its `code`.

- `code` (account number, e.g. `1930`; **immutable after creation** — it is the account's
  identity), `name`, `type` (`AccountType`), `description`, `is_active` (default true),
  `created_by_id` (raw column, no relation)
- **Unique `(organization_id, code)`** — codes are unique within a tenant; index
  `(organization_id, type)`
- Back-relation to `voucher_lines`. An account **referenced by any voucher line cannot be
  deleted** — it is deactivated instead (enforced in the service; the line FK is `Restrict`),
  preserving the audit trail

### fiscal_years

A financial year holding the periods that postings fall into.

- `name` (e.g. `2026`), `start_date`, `end_date` (both `@db.Date`), `status`
  (`FiscalPeriodStatus`, default `OPEN`)
- **Unique `(organization_id, name)`**; relation to `periods` (Cascade)

### fiscal_periods

A sub-period (typically a month) of a fiscal year. **A voucher can only be posted into a
period that covers its date and is `OPEN`.**

- `fiscal_year_id` (**Cascade**), `name` (e.g. `2026-01`), `start_date`, `end_date` (both
  `@db.Date`), `status` (`FiscalPeriodStatus`, default `OPEN`)
- Index `(organization_id, start_date)`; relation to `vouchers`
- Periods are validated **non-overlapping** at creation, so a date resolves to at most one
  period

### vouchers

The journal entry (verifikation). A double entry with ≥2 lines; the header stores the rolled-up
debit/credit totals.

- `number` (nullable until posted; assigned from the `VOUCHER` sequence on post), `date`
  (`@db.Date`), `description`, `status` (`VoucherStatus`, default `DRAFT`), `source`
  (`VoucherSource`, default `MANUAL`)
- `source_type` / `source_id` — a **loose reference** to the originating document (e.g.
  `invoice`/`payment`); deliberately **no FK**, so a voucher survives deletion of its source
  and stays idempotency-keyable
- `fiscal_period_id` (**SetNull**) — the covering period; informational on a draft, stamped
  authoritatively on post
- `total_debit_minor` / `total_credit_minor` (`BigInt`, default 0) — recomputed from the
  persisted lines on post (stored totals are never trusted)
- **Reversal self-relation** — `reverses_voucher_id` (nullable, **`@unique`**, `SetNull`)
  points from a reversing voucher to the original it cancels; the original exposes its
  reversal through the `reversedBy` back-relation (Prisma relation `VoucherReversal`). The
  `@unique` guarantees a voucher can be reversed **at most once**
- `reconciled_at` (nullable) — reconciliation status on a posted voucher; `posted_at`,
  `posted_by_id` (**SetNull**), `created_by_id` (**SetNull**)
- **Unique `(organization_id, number)`**; indexes `(organization_id, status)`,
  `(organization_id, date)` and `(source_type, source_id)` (the auto-draft idempotency lookup)

### voucher_lines

Ordered debit/credit lines belonging to a voucher. Cascade-delete with the voucher.

- `voucher_id` (**Cascade**), `account_id` (**Restrict** — see `accounts`), `description`,
  `debit_minor` / `credit_minor` (`BigInt`, default 0), `sort_order`
- **A line is either a debit or a credit** — exactly one side is positive, the other 0
  (enforced in the contract; posting re-sums both sides)
- Indexes `(voucher_id, sort_order)` and `(organization_id, account_id)` (the per-account
  ledger/trial-balance grouping)

### voucher_attachments

Receipt/underlag files for a voucher, stored in object storage like the Phase 2/3 attachments.

- `voucher_id` (**Cascade**), `uploaded_by_id` (**SetNull**), `file_name`, `content_type`,
  `size` (bytes, server-measured), `storage_key` (unique), `created_at`
- Index `(organization_id, voucher_id)`. Reuses the private-bucket / presigned-download model
  and the 25 MB / content-type allow-list (see [security.md](security.md#attachment-uploaddownload-phase-2))

### account_mappings

Per-organization default accounts driving auto-generated draft vouchers (configurable rules).

- **`organization_id` is `@unique`** — exactly one mapping row per organization
- `sales_account_id`, `output_vat_account_id`, `receivable_account_id`, `bank_account_id`
  (all nullable, raw columns) — the accounts the worker posts to when it drafts a voucher from
  an invoice or payment (see [architecture.md](architecture.md#event-driven-accounting-drafts-phase-5))

## Phase 6 — calendar & tasks

Added by migration `20260713183927_phase6_calendar`. Six new tables; every one carries
`organization_id` for tenant isolation and cascade-deletes with its organization. Times are
stored as `timestamptz` **UTC instants** (`starts_at`, `ends_at`, `occurrence_start`, …);
recurrence is not materialized into rows — it is a rule on the master event, expanded
server-side per query (see [architecture.md](architecture.md#server-side-recurrence-expansion-phase-6)
and [ADR-0007](decisions/adr-0007-server-side-recurrence-expansion.md)).

Enums:

- `CalendarType` — `TEAM` (default, shared) or `PERSONAL` (owner-only)
- `EventStatus` — `CONFIRMED` (default), `TENTATIVE`, `CANCELLED`
- `EventVisibility` — `DEFAULT` (default) or `PRIVATE` (visible only to organizer + attendees)
- `AttendeeResponse` — `NEEDS_ACTION` (default), `ACCEPTED`, `DECLINED`, `TENTATIVE`
- `ReminderMethod` — `EMAIL` (only method today)
- `RecurrenceFreq` — `DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY`
- `ExceptionType` — `CANCELLED` or `OVERRIDE`

### calendars

A calendar container. One **default** calendar per organization; team calendars are shared,
personal calendars belong to a single user.

- `name`, `color` (hex, default `#3b82f6`), `type` (`CalendarType`), `is_default` (default
  false), `created_by_id` (raw column)
- `owner_id` (nullable) FK to `users` (`CalendarOwner` relation, **SetNull**) — set only for
  `PERSONAL` calendars; null for `TEAM`. Deleting the owner detaches the calendar rather than
  removing it
- "At most one default per org" is enforced in the service (setting `is_default = true` clears
  the flag on the org's other calendars in the same transaction), not by a DB constraint
- Index `(organization_id, type)`

### calendar_events

The **master event** (series definition). A single event has `recurrence_freq = null`; a
recurring event stores its rule here and is never expanded into per-occurrence rows.

- `title`, `description`, `location`, `starts_at`, `ends_at` (both `timestamptz`), `all_day`
  (default false), `timezone` (default `Europe/Stockholm` — carried for display/all-day intent;
  instants are stored in UTC), `status` (`EventStatus`), `visibility` (`EventVisibility`)
- `organizer_id` (nullable) FK to `users` (`EventOrganizer` relation, **SetNull**)
- **Business context** `customer_id`, `project_id`, `task_id` — all nullable, all FK
  **SetNull**; the denormalized link chain mirrors the Phase 2 activity ref. A linked event
  posts an `event.scheduled` / `event.cancelled` activity onto that customer/project/task
  timeline
- **Recurrence fields** (a rule, not rows): `recurrence_freq` (`RecurrenceFreq?`, null =
  single), `recurrence_interval` (`Int`, default 1), `recurrence_by_weekday` (`Int[]`, UTC
  weekdays 0=Sun..6=Sat, `WEEKLY` only), `recurrence_count` (`Int?`) and `recurrence_until`
  (`timestamptz?`). `count` and `until` are **series-wide** (mutually exclusive in the
  contract)
- `created_by_id` (raw column)
- Relations: `organization`/`calendar` (**Cascade**), `organizer`/`customer`/`project`/`task`
  (**SetNull**), plus `attendees`, `reminders`, `exceptions`, `sent_reminders`
- Indexes `(organization_id, starts_at)`, `(calendar_id, starts_at)` and
  `(organization_id, customer_id)` — the range-window prefilter and the per-customer lookup

### event_attendees

A user invited to an event, with their RSVP.

- `event_id` (**Cascade**), `user_id` (**Cascade**), `response` (`AttendeeResponse`, default
  `NEEDS_ACTION`), `is_organizer` (default false)
- The **organizer is auto-added as an `ACCEPTED`, `is_organizer` attendee** on create and
  **cannot be removed** (409 `cannot_remove_organizer`) — enforced in the service
- **Unique `(event_id, user_id)`** (one row per user per event); index `(organization_id, user_id)`
  (a user's calendar / free-busy lookup)

### event_reminders

A per-event lead time that fires a notification before each occurrence.

- `event_id` (**Cascade**), `minutes_before` (`Int`, 0–40320 = up to 4 weeks), `method`
  (`ReminderMethod`, default `EMAIL`)
- Index `(event_id)`. On a series edit the reminder set is replaced wholesale

### event_exceptions

A **single occurrence** of a recurring series that has been cancelled or overridden. The
occurrence identity is the **original, rule-generated UTC start** it replaces, not a row id.

- `event_id` (**Cascade**), `occurrence_start` (`timestamptz` — the original rule start; the
  join key), `type` (`ExceptionType`)
- **Override fields** (all null when `type = CANCELLED`): `title`, `description`, `location`,
  `starts_at`, `ends_at`, `status`. An `OVERRIDE` may retitle/restatus a single occurrence or
  **move it** (`starts_at`/`ends_at`) — even into or out of a query window
- **Unique `(event_id, occurrence_start)`** — one exception per rule slot, upserted by the
  cancel/override endpoints; index `(organization_id, event_id)`

### sent_reminders

Worker idempotency ledger — one row per (reminder, occurrence) actually notified, so the
reminder sweep never double-fires.

- `event_id` (**Cascade**), `reminder_id`, `occurrence_start` (`timestamptz`), `sent_at`
- **Unique `(reminder_id, occurrence_start)`** — the authoritative guard. The claim row and
  the outbound emails are written in **one transaction**, so a duplicate claim rolls the whole
  batch back; the sweep is safe across restarts and overlapping runs (see
  [architecture.md](architecture.md#reminder-sweep-worker-job-phase-6)). Index
  `(organization_id, event_id)`

## Phase 7 — email

Added by migrations `20260715174559_phase7_email` and `20260715175000_phase7_email_constraints`
(the latter is raw SQL for a partial-unique index Prisma cannot express). Six new tables; every
one carries `organization_id` for tenant isolation and cascade-deletes with its organization.
This is **not** a full IMAP/SMTP client: outbound rides the existing worker email pipeline and
inbound arrives through the authenticated ingestion webhook (see
[architecture.md](architecture.md#email-phase-7)).

Enums:

- `EmailAccountType` — `SHARED` (default; visible to every email reader) or `PERSONAL`
  (owner-only)
- `EmailDirection` — `INBOUND`, `OUTBOUND`
- `EmailMessageStatus` — `DRAFT`, `QUEUED`, `SENT`, `FAILED`, `RECEIVED` (default)
- `EmailFolder` — `INBOX`, `ARCHIVE`, `TRASH` — the **physical** folder of a thread.
  **`SENT` and `DRAFTS` are computed views**, not stored values: `SENT` = the thread has an
  outbound `SENT` message, `DRAFTS` = it has a `DRAFT`, and the `INBOX` view excludes
  draft-only threads (see [architecture.md](architecture.md#folders-and-thread-aggregates-phase-7))

### email_accounts

A mailbox — one row per (organization, address).

- `address` (normalized lower-case), `display_name`, `type` (`EmailAccountType`),
  `provider` (default `manual` — reserved for future connected providers), `is_active`
  (default true), `created_by_id` (raw column)
- `owner_id` (nullable) FK to `users` (`EmailAccountOwner` relation, **SetNull**) — set only
  for `PERSONAL` mailboxes (the creator); null for `SHARED`
- **Unique `(organization_id, address)`** — one mailbox per address per tenant; index
  `(organization_id, type)`
- Deleting is rejected while the mailbox has threads (409 `account_in_use`) — deactivate
  instead

### email_threads

A conversation in a mailbox, carrying denormalized aggregates and the business-context links.

- `account_id` (**Cascade**), `subject` (**normalized** — reply/forward prefixes `Re:`,
  `Fwd:`, `Sv:`, … stripped; messages keep their raw subject), `snippet` (one-line preview of
  the last message), `folder` (`EmailFolder`, default `INBOX`), `is_starred`, `unread`,
  `message_count`, `last_message_at`
- `unread`/`message_count`/`last_message_at`/`snippet` are **recomputed from the messages in
  the same transaction** as any message write (`recomputeThread`); `unread` = any inbound
  message not yet read
- **Business context** `customer_id`, `project_id`, `task_id` — all nullable, all FK
  **SetNull**, mirroring the Phase 2/6 denormalized ref chain. `customer_id` is set by the
  inbound **auto-link** (sender matches a customer or contact email) or manually via the link
  endpoint; `task_id` is back-filled by **email → task**
- Indexes `(organization_id, account_id, folder, last_message_at)` — the folder list — and
  `(organization_id, customer_id)` — the per-customer lookup

### email_messages

A single email inside a thread.

- `thread_id` (**Cascade**), `account_id` (**Cascade**), `direction` (`EmailDirection`),
  `status` (`EmailMessageStatus`, default `RECEIVED`)
- Addressing: `from_address`, `from_name`, `to_addresses` (text[]), `cc_addresses` (text[]),
  `subject`, `body_text`, `body_html` (nullable — untrusted for inbound, see
  [security.md](security.md#email-privacy-and-inbound-webhook-authentication-phase-7))
- **RFC 5322 threading headers**: `message_id` (nullable — assigned on send for outbound,
  supplied by the provider for inbound; null on drafts), `in_reply_to`, `references` (text[])
- `is_read`, `sent_at`, `received_at`, `error` (the failure message when the worker marks a
  send `FAILED`), `created_by_id` (FK to `users`, **SetNull**, `EmailMessageCreatedBy`)
- Indexes `(organization_id, thread_id, created_at)`, `(organization_id, message_id)`,
  `(organization_id, status)`
- **Inbound idempotency backstop** — a **partial unique index**
  `(organization_id, message_id) WHERE message_id IS NOT NULL`
  (`email_messages_org_message_id_unique`, raw SQL in the `phase7_email_constraints`
  migration): at most one message per (organization, RFC Message-ID), making the inbound
  webhook's dedup race-proof while leaving drafts (null `message_id`) exempt

### email_attachments

Metadata for a file attached to a message, stored in object storage like the Phase 2
attachments (`storage_key` unique). Cascade-deletes with the message.

- `message_id` (**Cascade**), `file_name`, `content_type`, `size`, `storage_key` (unique)
- Index `(organization_id, message_id)`
- The table (and the DTO) exist, but **attachment upload/download UI is a documented future
  enhancement** — the demo does not send multi-attachment mail

### email_labels

Per-organization tags for threads.

- `name`, `color` (hex, default `#64748b`)
- **Unique `(organization_id, name)`** (409 `duplicate_label`)

### email_thread_labels

Thread ↔ label join table. Carries `organization_id` for consistency.

- Composite PK `(thread_id, label_id)` — attaching a label is an idempotent upsert
- Both FKs **Cascade**; index `(label_id)`

## Phase 8 — voice notes & telephony

Added by migration `20260717210840_phase8_recordings`. Two new tables; both carry
`organization_id` for tenant isolation and cascade-delete with their organization. Audio lives
in object storage (never in Postgres); transcription is produced asynchronously by the worker
through a pluggable STT seam (see
[architecture.md](architecture.md#voice-notes--transcription-phase-8) and
[ADR-0009](decisions/adr-0009-pluggable-transcription-seam.md)).

Enums:

- `RecordingSource` — `VOICE_NOTE` (default; uploaded audio, transcribed) or `CALL` (a
  telephony log with no audio)
- `RecordingStatus` — `UPLOADED` (default) → `TRANSCRIBING` → `TRANSCRIBED` / `FAILED`; the
  audio-processing lifecycle
- `CallDirection` — `INBOUND`, `OUTBOUND` (set only on call logs)
- `TranscriptStatus` — `NONE` (default; a call log has no transcript) or `PENDING` →
  `COMPLETED` / `FAILED` — tracks the transcript independently of `status`, so a stalled or
  failed transcription is distinguishable from the recording's own state

### recordings

A voice note or a call log.

- `source` (`RecordingSource`), `title`
- **Audio** (null for a call log): `storage_key` (**unique**, points at the object in storage —
  never exposed in the DTO; the DTO carries a derived `hasAudio` instead), `content_type`,
  `duration_seconds`, `size_bytes`
- `status` (`RecordingStatus`, default `UPLOADED`)
- **Call metadata** (source `CALL`): `direction` (`CallDirection`), `from_number`, `to_number`
- `occurred_at` — when the note/call happened (defaults to now on create); the list sort key
- **Transcription**: `transcript_status` (`TranscriptStatus`, default `NONE`), `transcript_text`
  (nullable — for a call log this is seeded from the `notes` field), `transcript_language`
  (BCP-47), `transcript_error` (the failure message when the worker marks it `FAILED`)
- **Business context** `customer_id`, `project_id`, `task_id` — all nullable, all FK
  **SetNull**, mirroring the Phase 2/6/7 denormalized ref chain. `task_id` is back-filled by
  **recording → task**
- `created_by_id` (FK to `users`, **SetNull**, `RecordingCreatedBy` relation)
- Indexes `(organization_id, source, occurred_at)` — the filtered list — plus
  `(organization_id, customer_id)` and `(organization_id, status)`

### transcript_segments

A time-coded segment of a recording's transcript (the worker rewrites the whole set on each
transcription, making re-transcription idempotent).

- `recording_id` (**Cascade**), `start_ms`, `end_ms`, `speaker` (nullable diarization label),
  `text`, `sort_order` (default 0)
- Carries `organization_id` for tenancy consistency
- Index `(recording_id, sort_order)` — the ordered read for the detail endpoint

## Tenancy rule for future tables

Every tenant-owned table added in later phases carries `organization_id` and is queried
only through the session-resolved active organization (see
[architecture.md](architecture.md#tenancy-model)). `users`, `outbox_messages`,
`processed_messages` and `failed_jobs` are intentionally global (identity and
infrastructure concerns).
